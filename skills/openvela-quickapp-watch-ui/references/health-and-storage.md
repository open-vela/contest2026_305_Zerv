# service.health 集成与 @system.file 存储最佳实践

> 适用：openvela 快应用（手表 / 手环）。结论在 `vela-miwear-watch-5.0` 模拟器实测。

---

## 一、`service.health` 集成要点

### 1. manifest 三件套，缺一不可

```json
{
  "features":    [{ "name": "service.health" }],
  "permissions": [{ "name": "hapjs.permission.HEALTH" }],
  "config": {
    "background": { "features": ["service.health"] }
  }
}
```

第三项 `config.background.features` 是**后台采集**时才需要，遵循最小权限原则按需开启。

### 2. 官方回调结构（已验证）

| 接口 | 结构 |
|---|---|
| `getRecentSamples.success` | `list = [{ dataType, data: { timeStamp, value } }, ...]` |
| `subscribeSample.callback` | `sample = { timeStamp, value }` |
| 两者 `fail(data, code)` | `code === 203` 表示**功能不支持** |

### 3. 使用要点

- **HEART_RATE 是 1Hz 逐秒回调**，等价于逐拍 BPM 流。
  可由 BPM 换算「估算间期」用于展示性波动统计，但**这不是逐搏测得的 RR 间期**，
  不能表述为临床 HRV。
- **冷启动先 `getRecentSamples` 补一帧**，避免首屏空白。
- **页面退出务必 `unsubscribeSample`**，防止后台空耗。
- **有效性过滤**：只接受合理范围（如心率 35～220），排除模拟器可能返回的
  `255` 无效值；检测超过 8 秒未更新则标记为过期。
- **大赛模拟器镜像内置 31 天真人数据回放**（HR 48～182 循环），
  无真机传感器也可完成全链路演示。

## 二、真机 vs 模拟器：哪些问题模拟器查不出来

**模拟器验证通过 ≠ 真机没问题。** 这是本项目付出较高排查代价换来的一条结论。

已知案例：`@system.storage`

- 在官方模拟器上，本地存储接口读写完全正常，功能验证全部通过；
- 把**同一份编译产物**安装到真机（小米手表系列）后，才出现本地存储读写不稳定的情况；
- 也就是说，**该问题在模拟器上无法复现**，开发阶段不会暴露，只能靠真机验证发现。

**结论**：

1. 涉及平台底层能力的接口（存储、传感器、权限、后台生命周期），**必须在真机上再走一遍完整流程**；
2. 存储一律用 `@system.file`，不要依赖 `@system.storage`；
3. 把"真机复验"写进发布前的检查清单，不要只跑模拟器就认为通过。

## 三、`@system.file` 存储最佳实践

### 1. URI 选择

| URI | 特性 | 用途 |
|---|---|---|
| `internal://files/` | **持久** | 长期数据 |
| `internal://cache` | 会被系统回收 | ⚠️ 长期数据**勿放** |

### 2. 内存写穿缓存（消除「写后立读」竞态）

高频小文件读写的核心手法：

- **写**：先落内存并**立即回调**，文件异步持久化；
- **读**：内存命中**直接返回**；
- 效果：消除「写完立刻读却读到旧数据」的竞态，并显著提速高频小文件读写。

### 3. 串行 I/O 队列

同一文件的读 / 写 / 删除操作**严格串行**，回调只在真实 I/O 完成后触发。
实现要点：

- 按文件名维护队列，每个队列同时只跑一个 job；
- job 完成（无论成功或失败）后 `drain` 下一个；
- 用 `finished` 标志防止回调被触发两次。

### 4. 小内存设备的文件保留策略

官方要求小内存设备及时清理文件。按日分文件的数据要做**保留策略**，
例如只保留最近 14 天，并**同步裁剪索引**，避免索引与实际文件不一致。

### 5. 结构化错误处理

所有存储操作返回 `(error, value)` 元组，调用方可区分不同场景：

- `code 301`：文件不存在 → 视为「空数据」，返回 `null` 而非报错；
- `JSON_PARSE` / `JSON_STRINGIFY`：序列化失败；
- 删除不存在的文件 → 视为**目标状态已达成**，返回成功。
